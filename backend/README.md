# Бэкенд Yandex Reviews

Laravel API отвечает за cookie-аутентификацию через Sanctum, хранение организаций и отзывов, фоновую синхронизацию через Redis queue и выдачу данных фронтенду.

## Требования

- PHP 8.3 или новее;
- Composer;
- PostgreSQL и Redis либо Docker Desktop с Laravel Sail.

## Локальный запуск

```bash
cp .env.example .env
composer install
```

Для PostgreSQL и Redis, запущенных на macOS вне Sail, до миграций измените в `.env`:

```dotenv
DB_HOST=127.0.0.1
REDIS_HOST=127.0.0.1
```

Внутри Sail оставьте `DB_HOST=pgsql` и `REDIS_HOST=redis`.

Затем подготовьте базу и запустите API:

```bash
php artisan key:generate
php artisan migrate --seed
php artisan serve --host=127.0.0.1 --port=8000
```

В отдельном терминале запустите worker:

```bash
php artisan queue:work redis --tries=4 --timeout=1800
```

Для локальной SQLite-базы можно изменить `DB_CONNECTION`, `DB_DATABASE`, `SESSION_DRIVER`, `CACHE_STORE` и `QUEUE_CONNECTION` в `.env`.

## Запуск через Sail

```bash
composer install
./vendor/bin/sail up -d
./vendor/bin/sail artisan key:generate
./vendor/bin/sail artisan migrate --seed
```

Запуск worker через Sail:

```bash
./vendor/bin/sail artisan queue:work redis --tries=4 --timeout=1800
```

## Основные переменные окружения

Полный и безопасный шаблон находится в `.env.example`. Файл `.env` с реальными паролями не коммитится.

| Группа | Назначение |
|---|---|
| `APP_URL`, `APP_PORT` | адрес и внешний порт API |
| `DB_CONNECTION`, `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` | подключение к PostgreSQL |
| `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD` | подключение к Redis |
| `QUEUE_CONNECTION`, `REDIS_QUEUE_RETRY_AFTER` | драйвер очереди и время до повторной выдачи Job |
| `SANCTUM_STATEFUL_DOMAINS`, `CORS_ALLOWED_ORIGINS` | доверенные адреса SPA |
| `DEMO_USER_NAME`, `DEMO_USER_EMAIL`, `DEMO_USER_PASSWORD` | учётная запись, создаваемая seeder |
| `YANDEX_MAPS_*` | тайм-ауты, повторы, лимиты и User-Agent парсера |

Настройки Sanctum, CORS и очереди для локального запуска:

```dotenv
APP_URL=http://localhost:8000
SANCTUM_STATEFUL_DOMAINS=localhost:5173,127.0.0.1:5173
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
QUEUE_CONNECTION=redis
REDIS_QUEUE_RETRY_AFTER=2100
```

В production нужно указать фактические HTTPS-домены, установить `APP_ENV=production`, `APP_DEBUG=false` и заменить демонстрационный пароль.

## Настройки парсера

```dotenv
YANDEX_MAPS_CONNECT_TIMEOUT=5
YANDEX_MAPS_TIMEOUT=20
YANDEX_MAPS_RETRIES=2
YANDEX_MAPS_RETRY_DELAY_MS=500
YANDEX_MAPS_MAX_PAGES=100
YANDEX_MAPS_MAX_REVIEWS=600
YANDEX_MAPS_USER_AGENT="Mozilla/5.0 ..."
```

`YANDEX_MAPS_MAX_REVIEWS` задаёт предел публично доступной SSR-выдачи. Достижение 600 уникальных отзывов считается успешным завершением, даже если в JSON указано больше страниц. `YANDEX_MAPS_MAX_PAGES` остаётся техническим предохранителем от бесконечной пагинации. User-Agent задаётся только через конфигурацию и не зашит в бизнес-логику.

## Модель данных

- `organizations` — ссылка, внешний идентификатор, название, рейтинг и счётчики компании;
- `reviews` — отзывы с уникальным внешним идентификатором внутри организации;
- `sync_runs` — состояние, прогресс и диагностическая ошибка каждого запуска;
- `organization_snapshots` — история рейтинга и счётчиков компании.

Удаление пользователя удаляет его организации, а удаление организации — связанные отзывы, запуски и снимки. Уникальные индексы не позволяют сохранить одну нормализованную ссылку дважды для одного пользователя.

## API организаций

Все маршруты ниже требуют активную сессию Sanctum. Чужая организация возвращает `404`, не раскрывая факт своего существования.

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/organizations` | Список организаций текущего пользователя |
| `POST /api/v1/organizations` | Проверка и сохранение ссылки Яндекс Карт |
| `GET /api/v1/organizations/{id}` | Данные одной организации |
| `GET /api/v1/organizations/{id}/sync-status` | Последний статус и прогресс синхронизации |
| `GET /api/v1/organizations/{id}/reviews?page=1` | Отзывы, по 50 записей на страницу |

Пример подключения:

```json
{
  "url": "https://yandex.ru/maps/org/example/123456/"
}
```

Поддерживаются HTTPS-ссылки раздела `/maps/` на доменах `yandex.ru` и `yandex.com`. Параметры запроса и завершающий слеш не влияют на проверку дублей.

При первом добавлении создаётся запуск со статусом `pending`, после чего API ставит `SyncOrganizationJob` в Redis queue. Worker меняет статус на `running`, обновляет прогресс после каждой страницы и завершает запуск статусом `completed`, `blocked`, `source_changed` или `failed`.

Одновременно может выполняться только одна задача для организации. Временные ошибки повторяются через 60, 300 и 900 секунд. Отзывы сохраняются через `upsert` по внешнему ID, поэтому повторный импорт не создаёт дубли. Новый снимок рейтинга и счётчиков сохраняется только при их изменении.

### Статусы синхронизации

| Статус | Значение |
|---|---|
| `pending` | Job создана и ожидает worker |
| `running` | парсинг выполняется, `progress` и `processed_reviews` обновляются |
| `completed` | данные атомарно сохранены |
| `blocked` | источник вернул HTTP 403/429 или CAPTCHA |
| `source_changed` | ожидаемое JSON-состояние или пагинация изменились |
| `failed` | исчерпаны повторы временного сбоя либо достигнут технический лимит |

## Подход к парсингу

Используется лёгкий гибридный подход без headless-браузера:

1. HTTP-клиент загружает публичную HTML-страницу карточки.
2. Из `<script class="state-view" type="application/json">` извлекается серверное JSON-состояние.
3. Из JSON читаются внешний ID, название, рейтинг, количество оценок и количество отзывов.
4. Парсер открывает публичные страницы отзывов `?page=1`, `?page=2` и далее. Каждая страница содержит до 50 отзывов и параметры пагинации; импорт завершается после 600 уникальных отзывов.
5. Отзывы объединяются по `reviewId`; повтор страницы или неожиданное окончание считаются изменением источника.

Внутренний XHR `business/fetchReviews` исследован, но не используется: он требует динамический браузерный параметр `s`. Воспроизведение этого защитного параметра сделало бы решение хрупким и приблизило бы его к обходу защиты. Публичные SSR-страницы дают те же структурированные данные без эмуляции Chrome.

| Подход | Плюсы | Минусы и риски |
|---|---|---|
| Публичный SSR JSON, выбран | быстро, мало памяти, не нужен Chrome, удобно тестировать fixtures | зависит от схемы JSON и публичной пагинации |
| Внутренний JSON/XHR | меньше HTML, удобная пагинация | динамический защитный параметр, риск частых поломок и обхода защиты |
| Headless-браузер | видит данные после JavaScript, ближе к поведению пользователя | медленная прокрутка, высокий расход RAM/CPU, хрупкие CSS-селекторы, тяжело масштабировать |

Headless-браузер можно добавить позже как диагностический адаптер за общим контрактом `OrganizationParser`, но не как скрытый обход CAPTCHA.

Парсер различает:

- `YandexMapsBlockedException` — HTTP 403, 429 или CAPTCHA;
- `YandexMapsSourceChangedException` — отсутствует JSON, показатели, отзывы или изменилась пагинация;
- `YandexMapsLimitExceededException` — технический лимит страниц достигнут раньше 600 отзывов; Job завершается без бесполезных повторов;
- `YandexMapsUnavailableException` — тайм-аут или HTTP 5xx.

Для временных сетевых и серверных ошибок выполняются ограниченные повторы. CAPTCHA не обходится. В логи нельзя помещать полный HTML, cookies и служебные параметры ответа.

Парсинг проверяется небольшими HTML-fixtures; автоматические тесты не обращаются к Яндекс Картам. Парсер вызывается только из фоновой Job, поэтому длительная операция не удерживает HTTP-запрос.

## Масштаб, антибан и дальнейшее развитие

Для сети из 50 филиалов уже реализованы фоновая Redis queue, прогресс, идемпотентное сохранение, запрет параллельного импорта одной карточки и ограниченные повторы. Количество worker-процессов нужно ограничивать на уровне Supervisor или Horizon.

Перед регулярным production-импортом следует добавить:

- общий rate limit на домен Яндекса, небольшой jitter между страницами и расписание без одновременного старта всех филиалов;
- экспоненциальный backoff с jitter для HTTP 429/5xx и общий circuit breaker при массовой блокировке;
- метрики длительности, числа запросов, повторов, блокировок и изменений схемы, а также alert на резкий рост ошибок;
- зашифрованный secret store для разрешённых прокси-учётных данных; сами адреса не должны попадать в Git и логи;
- регулярные fixture-тесты на разных типах карточек и ручной smoke-test по расписанию.

Если бы было больше времени, первыми шагами были бы rate limiter и наблюдаемость, потом плановая повторная синхронизация, отдельный адаптер для диагностики смены схемы и E2E-тест в браузере. Механизмы обхода CAPTCHA в план не входят.

Дополнительно доступны `POST /login`, `DELETE /logout`, `GET /api/v1/user`, `GET /up` и информационный `GET /`.
